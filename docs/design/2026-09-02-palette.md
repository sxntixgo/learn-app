## 1. Method

- **Conversion:** hex → linear sRGB (standard inverse gamma) → OKLab (`linearRgbToOklab` in
  `web/src/lib/oklch.ts`, unmodified) → OKLCH (`C = hypot(a,b)`, `H = atan2(b,a)`, both new —
  `oklch.ts` had no hex→OKLCH direction; the rest of the pipeline is `oklch.ts` as-is, not
  reimplemented). Script: `convert.mjs`, run via
  `node --experimental-strip-types` against the real `oklch.ts` import, kept in the session
  scratchpad, not the repo.
- **Precision:** L and C to 3 decimals, H to the nearest integer — matches `tokens.css`'s
  existing convention (every hue in the current file is a whole number).
- **Round-trip check:** OKLCH (at that rounded precision) → linear sRGB
  (`oklchToLinearRgb`) → hex (`toHex`), then ΔE between the original and round-tripped linear
  RGB via `perceptualDistance` (OKLab Euclidean distance), **×100** so the number sits on the
  familiar "ΔE ≈ 1 is a just-noticeable difference" CIE76-ish scale — OKLab's L/a/b are
  Björn Ottosson's deliberately-scaled analogue of CIE Lab, roughly 1/100th the magnitude, so
  raw OKLab distances of 0.01 are what CIE76 would call ΔE 1. `perceptualDistance` clips both
  inputs first, so this is a distance between what a screen actually shows, not between two
  idealized values.
- **Gamut:** every converted value checked with `inSrgbGamut`; all 32 are in-gamut with room
  to spare (no repeat of the `--color-accent-yellow` clipping bug).
- **Alpha values:** §5.2 gives several `rgba(...)` roles as a small sample of the alpha
  stops actually used (see §5). Where a token is baked from one, the doc shows the exact
  composite hex used for the ΔE check.

**Worst round-trip ΔE across all 32 direct hex→OKLCH conversions: 0.126**
(`--color-accent-gold`, light, `#C08A17` → `oklch(0.669 0.133 79)` → `#c08a18`). Every other
value round-trips at ΔE < 0.07. All comfortably under the ΔE < 1 floor.

## 4. Why some hexes moved role from what §5.2 says

§5.2 (the markdown spec) groups hexes by a short role label; reading the raw `.dc.html`
markup directly turned up three places where the actual CSS usage doesn't match that label:

1. **`#F0EEE9` ("Canvas / page") is not the app's page colour.** It is only ever the
   `<body>` background *around* the device-frame mockups (`body{background:#F0EEE9}`,
   1 occurrence). The screens' own background — what a real deployed page would show — is
   `#FDFCF7`/`#FBFAF6` (12 occurrences across `.padin`, the device-frame content area), which
   §5.2 filed under "Surface (raised)" instead. Dark mode's spec table already keeps Canvas
   (`#0E1112`) and Page (`#14191A`) as two separate rows with two separate hexes — this doc
   follows that split for light too, rather than light's combined row.
2. **`#25302E`/`#1F2A28` ("Dark surfaces (footer)") are text colours, not surfaces.** Every
   occurrence in the cached light artboard (16 total) sets `color:`, never `background:` —
   lesson-prose paragraphs (`#1F2A28`) and code/exercise-choice text (`#25302E`). No footer
   strip using either hex as a background was found in the artboards this doc had direct
   access to (see §6 — only 5 of 8 files were cached; this is not exhaustive).
3. **`#BFE4E9`/`#E5E3DA`/`#7FC3CB`/`#3F8E96` ("Teal banner / rail", "Border hairline", "Teal
   deep · mid · light") are literally the heatmap ramp.** `ipad-land-light.html` defines
   `const steps = ['#E5E3DA', '#BFE4E9', '#7FC3CB', '#3F8E96', '#0E5457']` and paints a
   336-cell activity grid from it, with a matching 5-swatch NONE→MORE legend at the bottom of
   the profile screen. The dark file's equivalent array is
   `['#252B2C', '#82B3BA', '#46909A', '#1E5055', '#072C2E']`. This resolves the plan task's
   flagged concern directly: the heatmap doesn't need new colours invented for it — the
   artboards build it entirely out of the border/rail/link family already in §5.2, and this
   doc's `--color-heat-*` tokens above are exactly that ramp, alias values and all — with one
   later exception: light step 0 no longer equals `--color-border-hairline`, because the
   ramp as drawn does not separate step 0 from step 1 for a protanope. See §5.7.

## 5. Judgement calls

### 5.1 Token set changes

- **Yellow → gold, same structural role.** `#C08A17`/`#8A6410` replace
  `--color-accent-yellow` doing exactly the job `CHOSEN-PALETTE.md` rule 1 gave yellow: the
  active-nav border/indicator and a callout's left edge. Renamed `--color-accent-gold` /
  `--color-accent-gold-text`.
- **Banner → rail.** The old `--color-banner-bg/text/divider` trio (a horizontal top strip)
  has no artboard counterpart — there is no top banner in the new design. The 224px teal
  rail is the new home for that chrome, so this doc retires the banner tokens and introduces
  `--color-rail-bg`/`--color-rail-text` in their place. No `--color-rail-divider`: the one
  divider line found in the rail (`rgba(191,228,233,.25)` in the account-settings nav) is an
  alpha of `--color-rail-text`, not an independent hex — left as a component-level choice for
  whoever writes the CSS, not promoted to a token.
- **Footer — likely retired, unconfirmed.** No artboard evidence of a `--color-footer-bg`
  analogue was found in the files this doc had cached access to (see §6). Flagged open rather
  than dropped outright.
- **`--color-track-*` (five hues) — no artboard source, left untouched.** Nothing in §5.2 or
  in the raw markup this doc inspected references a track/course-colour concept. Per the
  task's own instruction, no values are invented here. `db/migrations/0002_content_schema.sql`
  still constrains `hue` to `blue | teal | ochre | maroon | slate`, so the tokens must
  continue to exist with *some* value — recommend carrying the current `tokens.css` OKLCH
  values forward unchanged in task 2, since this doc has no artboard evidence to justify
  changing them.
- **`--color-heat-*` — resolved, not open.** See §4.3: the artboards supply an explicit
  5-step ramp (down from today's 6-step `--color-heat-0..5`), built from tokens already
  defined above. §5.6 below flags the one discrepancy in the dark ramp's step 0, and §5.7
  the one step of the light ramp that had to move to stay distinguishable.
- **`--color-heat-cell-edge` — no artboard source.** The heatmap cells in the markup
  (`13×13px`, `4px` gap, no `border`) rely on grid gap for separation, not a stroke. No hex
  corresponds to this token. Left open — carry the current value forward, or drop it, is a
  task-2/CSS call, not this doc's.
- **`--color-logo-tile` — likely retired, worth a second look.** The old rule was "pure white
  tile, mustard S never sits on a tinted field." The new logo mark observed in the rail is a
  2×2 checkerboard built directly from `--color-rail-bg`/`--color-rail-text` (`#0E5457`/
  `#BFE4E9` light, `#072C2E`/`#82B3BA` dark) — there is no white backing tile in what this doc
  inspected. Flagged open rather than deleted outright, since the icon might still sit on a
  white tile elsewhere (e.g. a favicon-style mark) that wasn't in the cached files.

### 5.2 Multiple hexes per role — how many surface tokens

Light's four near-whites collapse to **two** tokens (`--color-page`, `--color-surface-raised`
— `--color-surface-card` reuses `--color-surface-raised`'s value), not four:

- `#FDFCF7` vs `#FBFAF6`: ΔE 0.58 — imperceptible, same intended page tone drawn twice by
  hand. Canonical value: `#FDFCF7` (the CSS class default, used by the majority of screens).
- `#F4F3EC` vs `#F2F2EC`: ΔE 0.39 — same reasoning, folded to `#F2F2EC` (used far more
  often: 11 occurrences vs. 4, and across more roles).

Dark's equivalent hexes do **not** collapse the same way. `#222829` (surface-raised) and
`#1C2223` (surface-card) are 6/255 apart per channel — a real, visible step, not noise — and
serve genuinely different roles (larger structural panels vs. inset cards/rows). So dark gets
two distinct raised-surface tokens where light's evidence only supports one; light's
`--color-surface-card` is defined equal to `--color-surface-raised` to keep both themes
declaring the same token names (required by the `tokens.css` pattern — light/dark blocks
declare identical variable names), while honestly reflecting that light doesn't need the
distinction and dark does.

This is the same reasoning the plan's radii task uses: hand-drawn artboards carry variance
that isn't intent, and the fix is to look at how far apart the values actually are, not just
count how many hexes appear in the table.

### 5.3 The `rgba(...)` values

Two different situations, two different answers:

- **Text-secondary and border-hairline overlays** (`rgba(23,32,31,.55/.6/.45)`,
  `rgba(23,32,31,.12/.14)`, and dark's `rgba(236,239,238,…)` equivalents): the raw markup
  uses **23 distinct alpha stops** for text alone (light: .08 to .7; dark: .08 to .9), not
  the 2–3 §5.2 samples. This is not three intentional tiers — it is continuous hand variance
  around one semantic idea ("text, but quieter"), the same pattern as the surface duplicates
  above. **Decision: bake one representative alpha per theme to a solid OKLCH value**
  (`--color-text-secondary`), matching the existing `tokens.css` convention — the current
  file already bakes secondary text solid and uses no `rgba()` anywhere. Composited over
  `--color-page` (the ground text sits on almost everywhere it appears): light **`.65`** →
  `#686d6b`, dark `.72` → `#B0B3B3`. *(Light was `.6` → `#737875` until Phase 1 task 7
  measured it at 4.00:1 on a card. `.65` is the next stop the artboards themselves draw and
  the first of them that clears 4.5:1 — see §5.7.)*
- **`--color-tag-bg`**: this one *is* the alpha value itself (a genuinely translucent chip
  fill, `rgba(14,84,87,.12)` light / `rgba(70,144,154,.16)` dark, both alphas of `--color-link`
  over the page). Baked solid the same way, for the same reason — no alpha syntax elsewhere
  in `tokens.css` to be consistent with.
- **Border-hairline overlays** (`rgba(23,32,31,.1/.12/.14/.24/.28…)` on non-page grounds):
  not promoted to a token at all. `--color-border-hairline`'s existing solid value already
  covers the primary case (border on the page); the alpha variants seen on tinted surfaces
  are treated as a component-level opacity choice, the same category as the rail divider in
  §5.1, left to whoever writes the CSS.

### 5.4 `--color-text-reading` — a new token, folding a smaller but real gap

Light shows three near-black tones, not one: `--color-text` (`#17201F`, UI chrome),
`--color-text-reading` (`#1F2A28`, lesson prose), and a third (`#25302E`, code/exercise-choice
text) folded into `--color-text-reading` even though its ΔE from `#1F2A28` is 2.43 — a real,
measurable gap, an order of magnitude bigger than the surface folds above, but still small in
absolute terms and consistent with dark mode's explicit choice to collapse prose and code to
one value (`#D6DDDB`, "never pure white" per the brief). Folding is a judgement call, not a
rounding artifact — flagged with the actual number rather than silently absorbed, per the
task's instruction.

### 5.5 A contrast finding worth flagging (not this doc's to fix)

`--color-accent-gold` against `--color-rail-bg` — the active-nav border/indicator, gold's
main structural job — measures **2.84:1 in light mode**, computed with `oklch.ts`'s
`contrastRatio`. WCAG 1.4.11 puts the floor for non-text UI components (which a border/
indicator is) at 3:1. This is the same failure class `tokens.css`'s header comment on
`--color-accent-yellow` already documents at length (that one measured 2.46:1 against the
page). Dark mode's equivalent pairing clears the floor (3.93:1).

> **Resolved 2026-09-02, Phase 1 task 7 — and it does not resolve the way this section
> assumed.** Gold also fails on the page (2.97:1) and on a card (2.71:1), which this
> section did not measure. Those two are the cases where gold is the *only* signal, so
> `tokens.css` ships `oklch(0.596 0.124 79)` = `#a67500` (3.97 page / 3.63 card).
>
> The rail cannot be fixed at all, and the reason is arithmetic rather than a judgement
> call: light's `--color-page` and `--color-rail-bg` are **8.43:1** apart, so the best
> contrast *any* single colour can hold against both is `sqrt(8.43)` = **2.90:1** — under
> the floor before a value is even chosen. Darkening for the page necessarily costs
> contrast on the rail (`#a67500` is 2.13:1 there). The page and card win because on the
> rail the current item is *also* bold, in a different family, in a brighter text colour,
> on a tinted background — four redundant cues, where the callout's left rule and the
> activity dots have none. `palette.test.ts` asserts the impossibility, so a future palette
> that closes the gap re-opens the question instead of silently keeping the compromise.
>
> Note also that artboard-spec §5.2's "**2.25:1** on the rail" figure is measured against
> `#BFE4E9` — which is `--color-rail-text`, not the rail's ground. The rail's background is
> `#0E5457`, confirmed directly in `iPad Landscape Light` (`width:224px;background:#0E5457`
> on all seven screens). This section's 2.84:1 is the correct number.

### 5.6 One more discrepancy worth a human's eyes

The dark heatmap's own step-0 value, read directly out of the artboard's `steps` array, is
`#252B2C` — not `#2E3536` (the dark `--color-border-hairline` §5.2 gives, and the value light
mode's step 0 exactly reuses from its own border-hairline). ΔE between them is 3.91 — bigger
than any of the folds above. This doc maps dark `--color-heat-0` to `--color-border-hairline`
anyway, for symmetry with light's exact reuse and because `#252B2C` isn't listed anywhere in
§5.2 as its own token — but this is the least confident call in this document, and worth a
second look against the live canvas rather than the cached extraction this doc worked from.

### 5.7 The audit corrections (Phase 1 task 7)

`web/src/lib/palette.test.ts` gives every token a threshold matching the job it does and
measures it against the grounds the artboards actually put it on. Five values did not
survive that. Each is documented at length in `tokens.css` beside the value; the short
version:

| Token | Was | Is | Why |
|---|---|---|---|
| light `--color-accent-gold` | `#C08A17` | `#a67500` | 2.97 page / 2.71 card, floor 3:1 (a `border-left` ×9 / `background` ×3). §5.5. |
| light `--color-text-secondary` | `#737875` (the `.6` alpha stop) | `#686d6b` (the `.65` stop) | 4.38 page / 4.00 card, floor 4.5:1. Captions are 10–14px body text, not large text. |
| light `--color-heat-0` | `#E5E3DA` | `#f1efe6` | 0.0242 ΔEok from step 1 under protanopia (floor 0.04) and 1.055:1 in contrast (floor 1.15). |
| dark `--color-link` | `#46909A` | `#519ba5` | 4.07 on `--color-surface-raised` / 4.39 on `--color-surface-card`, floor 4.5:1. |
| dark `--color-accent-gold-text` | `#A67C25` | `#CFA23F` | Not a correction — a **transcription error in this doc**, fixed. See §3. |

Three of them deserve more than a table row.

**The light heatmap ramp, and why moving one step was not enough freedom.** The artboards'
light ramp starts `['#E5E3DA', '#BFE4E9', …]` — step 0 is `--color-border-hairline` and
step 1 is `--color-rail-text`, exactly as §4.3 found. Those two sit 0.021 apart in OKLCH
lightness and differ mostly in *chroma*, which is precisely what a protanope cannot see. A
heatmap cell is a filled square with no label, so colour is the only signal and design §10
asks specifically that the empty day be *clearly* distinct from level one. The pre-import
palette had solved this deliberately (its `--color-heat-0` was `oklch(0.945 0.004 95)`, a
near-white neutral); the artboard ramp regressed it.

Step 0 must stay the *lightest* step, so the only direction available is toward the page —
and the page is only so far away. The window is genuinely narrow: below L 0.945 step 0
collides with step 1, above L 0.959 the empty cell dissolves into the page and a quiet week
renders as a blank rectangle. `oklch(0.952 0.012 96)` sits in the middle (0.0479 ΔEok from
step 1, 0.0379 from the page), and `palette.test.ts` asserts **both** ends so neither can be
relieved by pushing on the other. Step 1 was left at the artboards' value because it is also
`--color-rail-text`, which carries a real 6.40:1 obligation on the rail; step 0 has no other
job.

**Dark's two golds.** §3 above previously gave `--color-accent-gold-text` the same `#A67C25`
as the indicator, on the strength of the brief's "bright enough for small labels, never
glaring". That was a frequency reading, and it is the same error artboard-spec §5.2's own ⚠️
note records for the light table. Reading the *property* each hex sets settles it: across the
four cached dark artboards `#A67C25` is `background` ×3 + `border-left` ×9 and `#CFA23F` is
`color` ×21. Two roles, two floors — and it matters, because `#A67C25` as text is 3.95:1 on
a raised surface. Spec §5.2's dark table had it right; this doc did not.

**Gold text on the light rail — spec §5.2.2's open question, answered: it never lands
there.** All 22 `color:#8A6410` occurrences in `iPad Landscape Light` are on the page or on
a card: the numbered list markers (01–05), "BROWSE CATALOG →", the lesson eyebrows
("LESSON SIX · 7 MIN"), the streak-day number, a literal in a code sample, and the
canvas-chrome `a:hover` rule. The rail's own text is `#fff` and alphas of `#BFE4E9`, never
gold. So the 3.96:1 figure spec §5.2.2 flags is a measurement of a pairing that does not
exist — and, separately, it was taken against `#BFE4E9` rather than the rail's actual
ground; against `--color-rail-bg` gold text is 1.62:1, which is worse and equally
hypothetical. `palette.test.ts` asserts the pairing stays illegal, so nobody introduces it
later on the belief that gold is "the accent colour" and therefore fine anywhere.

## 6. What this doc could not check

This doc was written against five of the eight artboard files, cached in the working
session's scratchpad from the Phase 0 extraction (`iPad Landscape Light`, `iPad Landscape
Dark`, `iPad Portrait Dark`, `iPhone Dark`, `Desktop Dark` — no light-mode file besides `iPad
Landscape Light` was available). Every hex in §5.2 was found and role-checked in at least one
of those five; nothing here required a file this doc didn't have. Still, three things a human
should confirm against the full eight-file set before treating §5 as final:

1. **The footer surfaces** (§5.1) — genuinely absent, or just not in the five files checked?
2. **The logo tile** (§5.1) — is there a white-backed version anywhere (e.g. a favicon), or
   is the checkerboard mark the only logo now?
3. **§5.6's dark heat-0 discrepancy** — `#252B2C` vs. `#2E3536`.
